Pick the tool that writes your `custom-elements.json`, by what each one reads
from your components and where its paths point. Skip this page if you only
want to turn the plugin's [`manifest`](/guides/manifest/) option on.

Every cell below comes from running the four tools on one small Lit library in
October 2026: an element that extends a mixin over a base class, with
decorators, JSDoc, a constructor, dispatched events, a vanilla element and a
barrel file. The versions were Lit DevTools 0.24,
[`@custom-elements-manifest/analyzer`][analyzer] 0.11.0 with `--litelement`,
[`cem`][cem] 0.11.4 and [`@lit-labs/gen-manifest`][gen] 0.3.6 through
`lit labs gen --manifest`. Follow the links for their current state.

## CEM analyzer

The analyzer is the reference most tools read against, and it reads the
widest syntax, frameworks beyond Lit included, through plugins. It lists private members and internal
state with their `privacy`, so a reader that wants the public API filters them
out. Its paths name your source files, so a published package needs a plugin
to point them at the built ones.

## cem

`cem` writes schema 2.1 and comes with tooling built on the manifest: a
language server, an MCP server, a dev server and a validator. On our library
it read decorated properties well on an element that extends `LitElement`,
but not on one that extends a mixin call. It doesn't merge inherited members,
infer dispatched events or read constructor defaults.

## Lit's gen-manifest

The Lit Labs generator runs the TypeScript checker, so it reports types you
never wrote, such as `string` for a parameter that defaults to `'info'`. Its
paths follow your tsconfig's `outDir`. It lists lifecycle and `@internal`
methods and doesn't merge inherited members. It is experimental, like the rest
of Lit Labs.

## Lit DevTools

The plugin reads your components the way its DevTools panel does, so the
manifest, the panel and Lit Inspector show the same docs. Under `vite build`
its paths name the files you ship, and tree-shaken components are left out.
In dev the manifest follows every edit. Its types are the text you wrote,
or a literal's own type where you wrote none, and the table's "No" rows are
what it doesn't read yet.
