## Hot patching that keeps state

Save a component and the page stays put. A hot patch is an edit applied to the
running page without a reload: the plugin updates the class in place, so
every element keeps its state. The indicator in the corner of the page pulses
green when a patch lands. Click the figure to replay the pulse.

<HmrIndicator
  state="update"
  count={3}
  alt="The HMR indicator after a component patch: the dot green, the count at 3."
/>

On by default. Guide: [Keep state across edits](/guides/hmr/).

## One stylesheet for every shadow root

Import a CSS file with `?css-sheet` and every component that imports it
adopts the same `CSSStyleSheet`. Save the file and the plugin swaps that
sheet's text: every shadow root restyles in place, nothing re-renders, and
the page keeps its state. Without it, saving the CSS reloads the page.

## Read every component's documentation

Select an element and the details pane shows what its author wrote: a
summary, what each property is for, the events it fires, its slots, parts
and CSS custom properties. The cart above is documented by a Custom Elements
Manifest it links. Your own components need none: their JSDoc is read from
source as you edit.

<DocsSources />

The same docs reach Lit Inspector and, through the `lit_component-docs` MCP
tool, your coding agent.

Guide: [Read a component's documentation](/guides/devtools/components/#read-a-components-documentation).

## Catch template mistakes in your editor

The language server completes your components' tags, attributes, properties
and events in `html` templates, and shows their docs on hover, read from the
same JSDoc. As you type, it reports what would go wrong in the browser; when
you save, it type-checks the file's bindings with your own TypeScript:

```ts title="src/x-app.ts"
html`<x-buton></x-buton>`;
//    ^^^^^^^ unknown-element: Did you mean `<x-button>`?
html`<x-button size="huge"></x-button>`;
//                   ^^^^ invalid-value: `size` takes one of `small`, `large`, not `huge`.
html`<x-button .size=${this.name}></x-button>`;
//                     ^^^^^^^^^ binding-type, on save: `.size` takes `"small" | "large"`, but this is `string`.
html`<div class=${styleMap(s)}></div>`;
//                ^^^^^^^^^^^ directive-binding: `styleMap` belongs to `style`.
```

It reads Lit templates, and custom elements in JSX, Astro, MDX and HTML
files. The same checks fail a CI run, through the Oxlint plugin and
`lit-devtools check`.

Guide: [Use the Lit language server](/guides/language-server/). Coming from
lit-analyzer: [Template checkers compared](/overview/compare-language-server/).

## Give your coding agent the page

The same component tree and timeline are MCP tools. An agent asks which
components re-rendered and why, and reads the answer from the running page
instead of guessing from the code.

Guide: [Connect a coding agent](/guides/devtools/agents/).

## Inspect sites you don't serve

Lit Inspector is the same panel as a browser extension. It works on
production builds and on any Lit site, with no Vite and no plugin.

Computed. Select any node there and the tab shows the Lit element at or
around it. Below, the Elements tree is drawn from the cart's real DOM and
