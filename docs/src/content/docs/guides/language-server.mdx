The Lit language server makes your editor understand your components: it
completes their tags, attributes, properties and events in `html` templates,
shows their docs on hover and types your event handlers. As you type it
reports what would go wrong in the browser: a tag, attribute or slot nothing
defines, a binding Lit reads differently than written, a directive where
Lit can't apply it, a value a binding can't take. When you save, it
type-checks the file's bindings with your own TypeScript. It reads your
sources as you type, so a component's docs are current before you save, and
it works in a project without Vite.
[Language server](/reference/language-server/) lists everything it does.

## Set it up in VS Code

<Steps>

1. Install [Lit DevTools][marketplace] from the Visual Studio Marketplace, or
   run **Extensions: Install Extensions** and search for `Lit DevTools`.

2. Install the package in your project, so the server's version matches it:

   ```sh frame="terminal"
   npm install -D @oddsquad/lit-devtools
   ```

3. Open a project and hover a component's tag in an `html` template.

</Steps>

[marketplace]: https://marketplace.visualstudio.com/items?itemName=oddsquad.lit-devtools

The extension runs the project's own `@oddsquad/lit-language-server` when the
project installs it, directly or through `@oddsquad/lit-devtools`, and the
copy bundled with it otherwise. To run a different build, point the
`lit.server.path` setting at its `dist/bin.mjs`. **Lit: Restart Language
Server** picks the server again, and the **Lit Language Server** output
channel says which one started.

Editors that install from Open VSX, such as Cursor and VSCodium, don't list
it yet. Until they do, build a `.vsix` in a checkout of the repository with
`pnpm install`, then `pnpm run build && pnpm run package` in
`packages/vscode`, and run **Extensions: Install from VSIX…** on it.

The type hints on event handlers are inlay hints, which VS Code shows unless
`editor.inlayHints.enabled` is off.

## Set it up in Zed

The Zed extension isn't in Zed's extension list yet. Install it from a
checkout of the repository; the server it runs comes from npm.

<Steps>

1. In a checkout of the repository, run **zed: install dev extension** from
   Zed's command palette and pick `packages/zed`. Zed compiles it, which
   needs Rust from [rustup](https://rustup.rs).

2. Install the package in your project, so the server's version matches it:

   ```sh frame="terminal"
   npm install -D @oddsquad/lit-devtools
   ```

   Without it, the extension installs the latest server from npm itself.

3. Open a project and hover a component's tag in an `html` template.

</Steps>

To run a server you built yourself, point Zed's settings at its
`dist/bin.mjs`:

```json title="~/.config/zed/settings.json"
{
  "lsp": {
    "lit-language-server": {
      "binary": {
        "path": "/path/to/lit-devtools/packages/lit-language-server/dist/bin.mjs"
      }
    }
  }
}
```

The type hints on event handlers are inlay hints, which Zed shows when
`"inlay_hints": {"enabled": true}` is set.

## What it reports

Problems show in Lit templates, and for custom elements in JSX, Astro, MDX
and HTML files:

- **Names nothing defines.** `<x-buton>`, `sise="small"`, `.cont=${1}` or
  `slot="heder"`, each with the name you probably meant.
- **Values a binding can't take.** `size="huge"` when `size` is
  `'small' | 'large'`, a string in `?hidden=${'no'}`, a handler whose
  parameter doesn't fit its event.
- **Templates Lit reads differently than written.** A component closed
  with `/>`, `.value="x"` without `${…}`, a stray quote next to an
  expression.
- **Directives in the wrong place.** `classMap` outside `class`, `ifDefined`
  on a property, `repeat` in an attribute: each throws on first render.
- **Mistakes in a component's declaration.** A tag `customElements.define`
  refuses, an `attribute:` name HTML lowercases away, a field that replaces
  an element's own method, such as `@state() after`.

Each kind is a rule with its own severity, which `diagnostics` sets; the
[rules table](/reference/language-server/#settings) lists them all.

<Aside title="New warnings after upgrading to 0.25">
  0.25.0 added most of these rules, and several are on by default, so a project
  that was clean before may show warnings. Fix them, set a rule's severity in
  `diagnostics`, or silence a spot with a comment, as below.
</Aside>

### Silence a problem

A `lit-ignore` comment silences the problems it covers, in the editor, in
Oxlint and in `lit-devtools check`. Name the rules, or none for all of them:

```ts
html`
  <!-- lit-ignore unknown-attribute -->
  <x-legacy colour="red"></x-legacy>
`;

// lit-ignore-next-line binding-type
html`<x-button .size=${this.name}></x-button>`;
```

Inside a template the comment is an HTML one, and covers the next element.
`// lit-ignore-file` anywhere in a file covers all of it.

### Components from a library without a manifest

The server knows a library's components from the Custom Elements Manifest
the library ships. A library that ships none shows up as unknown elements.
List a manifest for it, a path in your project or a URL, in `manifests`, and
its components complete, show their docs and are checked like any other:

```ts title="vite.config.ts" ins={3}
litPlugin({
  languageServer: {
    manifests: ['./manifests/legacy-ui.json'],
  },
});
```

With no manifest to hand, name its tags in `ignoreTags`, `'legacy-*'` for a
whole prefix, and they're accepted without being checked.

### Catch components a file never imports

A tag renders as an empty element when nothing imports its definition.
`missing-import` reports a component a file uses but never imports, directly
or through the modules it imports, and its quick fix adds the import. It's
off by default; an app whose entry imports every component lists that entry
in `entries`, so what it imports counts for every file:

```ts title="vite.config.ts" ins={3-4}
litPlugin({
  languageServer: {
    diagnostics: {'missing-import': 'warning'},
    entries: ['src/main.ts'],
  },
});
```

## Configure it

The server needs no settings. To change what it reads or how loud a problem
is, set `languageServer` in your Vite config:

```ts title="vite.config.ts" {6-9}
import {defineConfig} from 'vite';
import {litPlugin} from '@oddsquad/lit-devtools/vite';

export default defineConfig({
  plugins: [
    litPlugin({
      languageServer: {
        diagnostics: {css: 'off', 'event-type': 'warning'},
      },
    }),
  ],
});
```

In a project without Vite, put the same settings in a
`lit-devtools.config.ts` (or `.mts`, `.js`, `.mjs`, `.json`) next to its
`package.json`:

```ts title="lit-devtools.config.ts"
export default {
  languageServer: {
    scan: ['src', 'lib'],
    cssTemplateTags: ['css', 'styles'],
  },
};
```

When a package has both, the Vite config's `languageServer` wins as a whole,
and the config file gets a warning saying it's ignored: the two are never
merged key by key. A `.ts` config file needs Node 22.18 or later; a `.js` or
`.json` one works on any. The
[settings reference](/reference/language-server/#settings) lists every key.

## Check it in CI with Oxlint

The same problems can fail a lint run. Install `@oddsquad/lit-devtools` next
to Oxlint and extend its Oxlint plugin's recommended config, which turns each
rule on at the severity the editor gives it:

```sh
npm install -D oxlint @oddsquad/lit-devtools
```

```ts title="oxlint.config.ts"
import {defineConfig} from 'oxlint';
import litDevtools from '@oddsquad/lit-devtools/oxlint';

export default defineConfig({
  extends: [litDevtools.configs.recommended],
  rules: {'lit-devtools/css': 'off'},
});
```

Rules set next to `extends` win, as `lit-devtools/css` does here. With
Vite+, the same object goes under `lint` in `vite.config.ts`. A project that
wants only the rules installs `@oddsquad/oxlint-plugin-lit` and imports from
it instead. In an `.oxlintrc.json`, list the plugin and its rules yourself:

```json title=".oxlintrc.json"
{
  "jsPlugins": ["@oddsquad/lit-devtools/oxlint"],
  "rules": {"lit-devtools/event-type": "error", "lit-devtools/css": "warn"}
}
```

- Oxlint's config decides each rule's severity; the `diagnostics` setting is
  for the editor only. The other settings, such as `scan`, apply to both.
- Silence one spot with a [`lit-ignore` comment](#silence-a-problem), or
  with Oxlint's own, `// oxlint-disable-next-line lit-devtools/event-type`.
- Oxlint reads JavaScript and TypeScript files, so problems in HTML, Astro
  and MDX pages still show only in the editor.
- The first file waits while the plugin reads the workspace, once per run.

### Type-check bindings with TypeScript

As you type, the editor and Oxlint read types as text, so they catch
`.size=${'huge'}` but not `.size=${this.name}` when `name` is any `string`.
That takes your project's TypeScript. The editor runs it over a script's
bindings when you save the file, and shows what it finds until you edit
again; set `checkOnSave: false` to turn that off. In CI, run it over every
script next to the lint run:

```sh
npx lit-devtools check
```

Both need `typescript` in the project, 5 or 7, and each component in
`HTMLElementTagNameMap`, which is where they read what an element takes. A
component missing there is reported as `missing-element-type`, and its
quick fix, or `oxlint --fix`, writes the entry.
[`lit-devtools check`](/reference/cli/#lit-devtools-check) lists what it
checks and what it skips.

## Use it in a monorepo

Open the monorepo at its root. The server finds the workspace from a
`pnpm-workspace.yaml` or a `workspaces` field in `package.json`, and reads
every package in it:

- Each package is read with its own settings and its own Vite config, so its
  aliases apply.
- A component can extend a base class from another workspace package; its
  inherited attributes and properties show up.
- A tag from a published library completes only in the packages that depend
  on that library.

## When nothing shows up

- Check that the server started: in VS Code, the **Lit Language Server**
  output channel; in Zed, **dev: open language server logs**.
- After rebuilding the server, restart it: **Lit: Restart Language Server**
  in VS Code, **editor: restart language server** in Zed.
- Check the settings file for a warning on its first line: a mistake there is
  reported, not thrown.
- With another Custom Elements Manifest server installed, such as the Web
  Components Language Server, hovers appear twice; disable one.
